# JAMO 진행 및 수정 히스토리

*설계서(`JAMO_benchmark_design.md` v5, `JAMO_v51_patch.md`)를 실제로 구현하면서
쌓인 기록. 설계 문서가 "무엇을 왜 이렇게 설계했는가"라면, 이 문서는
"구현하면서 실제로 무엇을 만들었고 무엇이 깨졌고 어떻게 고쳤는가"를 남긴다.*

## 5단계 — 결정적 버그 발견: Route 분류 오염

T1/T2 격차와 "와"(완벽하게 그려진 클린 이미지)가 A0로 잘못 분류된 사례를
교차검증하면서, **`build_detection_input`의 `has_text_like_region`이
`len(fields) > 0`(= "OCR이 뭐라도 찾았는가")로 근사되어 있었다는 것**을
발견. 이는 v5.1 §5가 정확히 경고한 실패 모드 — "프롬프트 실패 ∪ 렌더
실패 ∪ OCR 실패"를 한 버킷에 섞는 것.

**실증**: 이미지의 잉크 bbox 높이 비율을 Route별로 재보니 완벽한 단조
관계(글자가 클수록 나쁜 Route로 분류). T1 중앙값 0.530, T2 중앙값 0.362 —
CLOVA 실패 임계선(0.3~0.5 구간)과 정확히 겹침. "와" A0 이미지에 **잉크는
그대로 두고 여백만 추가**하자 CLOVA가 정상 검출 — 이미지 자체엔 문제가
없었다는 결정적 증거.

**수정 3건**
1. `vision_heuristics.py`(신규): `has_ink_marks()` — OCR 성공 여부와
   무관하게 이미지 픽셀만으로 "글자 시도가 있었는가"를 판정.
2. `route.py`: `build_detection_input()`이 `has_text_like_region`을
   호출부가 명시적으로 넘기도록 시그니처 변경(암묵적 OCR 의존 제거).
3. `judge_preprocess.py`(신규): `normalize_occupancy()` — OCR에 넣기
   전 잉크 bbox가 캔버스의 target_max_occupancy를 넘으면 다운스케일.
   실제 생성 이미지로 재검증한 결과 0.35도 부족한 사례가 있어(실측:
   "와" 0.35 실패, 0.25 성공) 기본값을 0.28로 최종 고정.

`scripts/run_pilot.py`도 두 함수를 쓰도록 갱신. 129개 테스트.

## 6단계 — CLOVA의 희귀 음절 사전 편향 발견

18셀 × 대표음절 1개 × 6장(clean 2 + degraded 4) 규모로 첫 Ceiling 실측을
돌린 결과 **18셀 전부 `official_excluded`**(degraded < 90%), 다수 셀이
클린 렌더링에서도 0%.

폰트 렌더링 자체가 잘못됐는지 확인하기 위해 문제 셀 중 하나("콃" =
ㅋ+ㅖ+ㄼ)를 직접 렌더링해 육안 확인 — **완벽하게 선명한 글자**였다.
같은 이미지를 CLOVA에 넣자 confidence 0.33으로 **"켸래"라는 존재하지
않는 두 글자로 오판독**. 이미지 품질 문제가 아니라 **CLOVA가 내부적으로
"그럴듯한 실제 한국어 단어" 쪽으로 글자를 끌어당기는 언어모델 편향을
가졌다**는 결론.

이는 설계서 §8.1이 CLOVA를 Primary가 아니라 **Reference(secondary)
judge**로 설계한 이유와 정확히 맞아떨어진다 — 그런데 이번 구현에서는
API 키가 바로 있었던 CLOVA로 전체 파이프라인을 만들었기 때문에, 원래
계획된 "OSS OCR을 Primary로" 단계를 아직 밟지 않은 상태였다.

**사용자 결정**: 한국어 OCR 품질과 크레딧 여유를 근거로 OSS OCR(PaddleOCR
등) 전환 대신 **CLOVA를 계속 판정자로 사용**하고, 대신 표본을 키워 신뢰할
수 있는 Ceiling 표를 만들기로 함.

### Ceiling 측정 확대 + 안정성 보강

- `scripts/measure_ceiling.py`: 셀당 대표음절 1개 → **5개**, degraded
  샘플 3개로 확대(셀당 40장, 18셀 합계 720장).
- 첫 확대 실행 중 소켓 읽기 단계의 `TimeoutError`로 6/18셀 진행 후 크래시
  (이 예외는 urllib이 `URLError`로 감싸지 않고 그대로 전파 — 기존
  `clova_ocr.py`는 이를 잡지 못했다). 이미 쓴 API 호출이 저장 없이

- 수정: `clova_ocr.run_general_ocr()`에 재시도(`MAX_RETRIES=3`, 지수
  백오프) 추가, `measure_ceiling.py`를 셀 단위로 즉시
  `results/judge_ceiling_cells.jsonl`에 저장하고 재실행 시 완료된 셀은

- 720장 규모 재측정 완료: **18셀 전부 `official_excluded`**(전체 clean

  노이즈가 아니라 구조적 현상.

## 7단계 — 사람 감사로 CLOVA 실격 확정

CLOVA 내부 대안부터 확인: General / Template / Document 세 도메인 중
General이 이미 가장 덜 구조화된 모드이고, API 파라미터에도 사전·언어모델
보정을 끄는 옵션이 없다(공식 문서 확인). **CLOVA 안에는 대안이 없다.**

그래서 사람 감사를 앞당겨 실행. `scripts/audit_server.py` +
`audit_ui.html`로 로컬 웹 UI 구축 — Ceiling 측정에서 CLOVA가 봤던 것과
**동일한 clean 렌더링 180장**(`forge_render.render_clean()`이 결정론적이라
재생성 가능)을 target-blind로 제시하고 자유 전사를 받는다(§9.2).

### 결과 (감사자 1인, 180문항 전수)

| | 사람 | CLOVA |
|---|---|---|
| 전체 정확도 | **99.4%** (179/180) | **32.8%** |
| 사람↔CLOVA 일치율 | **32.8%** | |

| 종성 유형 | 사람 | CLOVA |
|---|---|---|
| 없음 (no_T) | 100.0% | 75.0% |
| 단순종성 (simple_T) | 100.0% | 20.0% |
| 겹받침 (cluster_T) | 98.3% | **3.3%** |

사람의 유일한 오답은 가장 어려운 셀의 `끣`→`뀏` 1건.

### 판정: CLOVA는 Primary judge로 실격

설계서 §14.2의 No-Go 조건이 문자 그대로 발동했다 —
**"사람–OCR 일치율 85% 이하 → 공식 점수 주장 폐기"**(실측 32.8%).
§8.1의 에스컬레이션 규칙("<90% 셀이 전체의 20% 초과 → primary/reference
재역전 또는 VLM judge 후보 평가")도 최대치로 발동(100% 셀 미달).

**단, 프로젝트 자체의 No-Go는 발동하지 않았다.** 같은 §14.2가 중단 조건을
"ceiling 미달 **+ 사람 감사도 불안정**"으로 정의했는데, 사람 감사는
99.4%로 매우 안정적이다. 즉 **이미지는 원리적으로 측정 가능하며, 실격된
것은 CLOVA라는 특정 판정자 하나**다.

### 지금까지의 Seedream 수치는 해석 불가 — 천장 보정도 불가능

동일 지표(음절 완전일치)로 CLOVA 천장과 Seedream 실측을 비교하면
**Seedream이 천장을 초과**하는 모순이 나온다:

| 종성 유형 | CLOVA 천장 | Seedream 실측 |
|---|---|---|
| no_T | 75.0% | 45.9% |
| simple_T | 20.0% | **33.0%** ← 천장 초과 |
| cluster_T | 3.3% | **10.8%** ← 천장 초과 |

두 실험에 공통 등장한 41개 음절을 1:1 대조하면 원인이 드러난다 —
판정자가 **글자의 정오와 무관한 이유(글리프 스타일)로 흔들린다**:

- `값`: 완벽한 폰트 렌더링 **0%** vs Seedream 생성물 **80%**
- `게`·`깨`·`쬐`: 폰트 **100%** vs Seedream **0%**

오차가 한 방향이 아니라 양방향이므로 **단순 감산이든 비율 보정이든
천장 보정 자체가 성립하지 않는다.** 5단계에서 얻은 v2 수치(초성 88.7 /
중성 57.4 / 종성 48.4)와 헤드라인이었던 "종성 붕괴" 패턴은 **모델의
실패인지 CLOVA의 실패인지 분리 불가능**하다 — CLOVA 자신의 천장이 정확히
같은 축(종성 복잡도)을 따라 무너지기 때문이다.

> **부수 소득:** "상용 한국어 OCR이 사람은 99.4% 읽는 완벽한 희귀 음절
> 렌더링을 67% 오독한다"는 것 자체가 정량화된 방법론적 발견이며,
> JAMO가 `OCR-mediated`라는 한계를 이름에 박아둔 이유를 실증한다.
> 동시에 **사람 검증된 180문항 골드셋**을 확보했으므로, 앞으로 어떤
> 판정자 후보든 이 세트로 즉시·무료·로컬 검증할 수 있다.

## 8단계 — VLM judge 시도, 글자 크기가 핵심 변수였음을 발견, 판정자 문제의 완전한 분해

### VLM judge 구현과 좌절

§8.1 폴백("오픈 가중치 VLM judge 후보 평가")에 따라 `vlm_judge.py` 구현.
SPARK와 같은 ModelArk 계정의 VLM 엔드포인트(`ARK_MODEL_VLM`)를 재사용하되,
CLOVA의 실패를 반복하지 않도록 설계했다 — "무슨 글자냐"를 통짜로 묻지
않고 **초성/중성/종성을 보이는 형태 그대로 답하게** 한 뒤
`decompose.compose()`(신규, decompose의 역함수)로 우리가 직접 조립한다.
모델이 "그럴듯한 실제 단어"로 답을 바꿀 형식적 여지 자체를 없앤 것.

소규모 실측(5건): 응답한 2건("읽"→ㅇ+ㅣ+ㄺ, "와"→ㅇ+ㅘ)은 **정확히 자모
단위로 분해해서 맞혔다.** 그러나 3건은 90초 타임아웃. 원인 진단 결과 —
**네트워크 문제가 아니라 추론형(reasoning) 모델이 어려운 글자에
과도한 내부 추론을 쓴다**("값" 성공 사례: 273.9초, completion 19,927
토큰 중 19,856이 reasoning 토큰). 어려운 케이스일수록 더 오래 걸리고
결국 타임아웃 나는 패턴이라, **CLOVA의 사전 편향과 같은 자리에 다른
얼굴로 나타난 동일한 문제**(판정자 실패가 난이도 축과 상관됨)로 판정,
현재 규모(3,240장)에는 비실용적이라 보류.

### 사용자 제안으로 핵심 변수 발견: "글자 크기" 그 자체

사용자가 "네이버 OCR은 문서 속 작은 글자 위주로 학습됐을 텐데, 초대형
글자를 읽는 데 한계가 있지 않냐"고 지적. 점유율을 0.28→0.03까지 7단계로
훑어 **실사용 흔한 음절**(이그해가/간곧각감/값많짧읽)로 검증:

| 점유율 | no_T흔함 | simple_T흔함 | cluster_T흔함 | cluster_T희귀 |
|---|---|---|---|---|
| 0.28(기존) | 25% | 50% | 25% | 0% |
| 0.10 | 100%(deg 75%) | 100% | 100% | 0% |
| 0.05 | 100% | 100% | 75%(열화 시) | 0% |

**흔한 글자는 크기만 맞추면 전부 100%에 수렴한다.** 겹받침이라서
낮았던 게 아니라 크기가 문제였다. 단, degraded(블러/노이즈) 조건까지
포함해 검증하니 **너무 작으면(0.05) 겹받침의 미세 획이 뭉개져 오히려
정확도가 떨어졌다**(100%→75%) — "작을수록 좋다"가 아니라 clean/degraded
양쪽에서 가장 안정적인 **0.10**을 최종값으로 채택
(`judge_preprocess.TARGET_MAX_OCCUPANCY = 0.10`, recipe v2).

**반면 희귀 조합(콃, 띘 등)은 0.28부터 0.03까지 전 구간에서 0%.** 크기와
완전히 무관한 별개의 문제라는 것이 확정됐다.

### 골드셋 재검증으로 두 원인을 완전히 분리

180문항 골드셋(사람 라벨은 그대로 재사용, CLOVA 읽기만 occ 0.10으로
재실행)을 돌린 결과, 전체 정확도는 32.8%→35.6%로 거의 안 움직였다 —
언뜻 크기 보정이 무의미해 보였으나, 원인을 파보니:

**겹받침 셀 60문항 중 실사용 음절은 "값"·"읽" 단 2개뿐이고 나머지
28개(콃·탢·톊·햵...)는 전부 실사용에 없는 조합**이었다. 이 2개만 떼어
보면:

| 음절 | v1(occ 0.28) | v2(occ 0.10) |
|---|---|---|
| 값 | ✗("가") | **✓** |
| 읽 | ✓ | ✓ |

**실사용 음절 기준 정확히 100%.** 나머지 28개 희귀 조합은 v1/v2 무관하게
0%. 골드셋 전체 정확도가 안 움직인 건 셀 안에 희귀 조합이 압도적으로
많아서(93%) 크기 보정 효과가 평균에 묻힌 것뿐, **크기 보정 자체는
완벽하게 검증됐다.**

### 결론 — 판정자 문제가 완전히 두 축으로 분해됨

| 원인 | 증상 | 해법 |
|---|---|---|
| **글자 크기** | 문서 OCR 학습분포 밖의 초대형 글자 | `judge_preprocess.normalize_occupancy(target=0.10)` — **해결됨** |
| **음절 희귀도** | 언어모델/사전 기반 판정자가 실사용에 없는 조합을 "교정"하려 함 | 인식 기반 판정자(OCR·VLM 불문) 전부 원리적으로 불가능. 유일한 대안은 **폐쇄형 검증**(타깃 후보를 폰트로 렌더링해 이미지 유사도로 대조 — "이게 뭐야?" 대신 "이게 A야?") |

동시에 이 발견은 Core 셀 설계 자체의 성질도 드러냈다: `complex_V ×
cluster_T` 같은 셀은 "구조적 완전성" 기준으로 채우면 **표본의 90%
이상이 실사용에 없는 조합**이 된다 — 어떤 판정자를 쓰든 이런 셀은
인식 기반으로는 채점 불가능하다는 뜻이며, 이 결론은 이제 감으로 하는
추정이 아니라 실측으로 확정됐다.

### 미해결 — 이중 판정자 체계 설계 필요

다음 단계로 논의 중: 실사용 음절이 대다수인 셀은 CLOVA(+occ 0.10)로,
희귀 조합이 대다수인 셀은 템플릿 매칭(폐쇄형 검증, 미구현)으로 나눠
채점하는 구조. 아직 구현 시작 전.

### Seedream 300장의 현재 위치

파일럿 300장(images 포함)은 그대로 보존돼 있으며 **아직 신뢰할 수
있게 채점된 적이 없다**(v1: Route 버그, v2: occ 0.28 버그, 둘 다 무효).
오늘의 모든 실험(크기 스윕·degraded 검증·VLM·골드셋 재검증)은 전부
**폰트 렌더링만 사용, Seedream 신규 호출 0건.** 이중 판정자 체계가
확정되면 이 300장을 세 번째로(v3, 생성 비용 0) 재채점해 "사람 검증
기준 Seedream 실제 성능"의 첫 신뢰 가능한 답을 낸다. 그 전까지는
Core 3,240장으로 확대하지 않는다 — 판정자를 못 믿는 상태에서 대량
생성하면 같은 실수를 세 번째 반복하게 된다.

## 9단계 — 폐쇄형 검증(템플릿 매칭) 구현, CLOVA를 실측으로 능가

### 설계

CLOVA·VLM 둘 다 "이게 무슨 글자냐"는 개방형 인식(사전/언어모델 개입)을
푼다. `jamo_bench/template_match.py`는 다른 질문을 푼다 — **"이 모양이
11,172개 완성형 음절 중 어느 것과 가장 닮았는가"**. 순수 이미지 유사도
비교이며 언어 지식이 전혀 없어 사전 편향이 구조적으로 불가능하다.

1. 11,172자 전부를 OFL 폰트로 렌더링해 정규화된 흑백 마스크 템플릿을
   1회 캐싱(로컬, 무료, API 호출 0건 — 2폰트 66.6초)
2. 판독 대상 이미지의 잉크 bbox를 잘라 같은 방식으로 정규화
3. 가장 닮은 템플릿을 채택 → 그 문자를 OCR의 candidate_text 자리에 꽂아
   기존 score.py/route.py/match_region.py를 그대로 재사용

### 실패 1 → soft-IoU로 해결

초기 버전(이진 IoU)은 실제 Seedream 이미지에서 명백한 정답 "읽"이 더
닮은 "엵"에 밀리는 사례가 나왔다 — 가는 획은 JPEG 압축·리샘플링으로
1~2px만 어긋나도 겹치는 면적이 급격히 준다. 두 마스크에 동일한 가우시안
블러(σ=3)를 씌운 뒤 min/max 중첩 비율(soft-IoU)로 비교하니 해결(육안상
명백한 정답이 실제로 1위로 올라옴, 콃도 정확히 잡아냄).

### 실패 2 → 폰트 스타일 다양화로 해결

30장 표본 검증(52.0%는 나중 결과, 최초 시도는 26.7%→soft-IoU 후 36.7%)
에서 템플릿 폰트(Noto Sans KR·Pretendard, 둘 다 산세리프)와 스타일이
다른 T2 프롬프트("printed ink... studio photo") 출력이 체계적으로
낮았다: T1 44.4% vs T2 25.0%. 원인은 스켈레톤화 시도(획 두께 정규화)로도
못 고쳤다 — 붓글씨체의 둥근 모서리가 스켈레톤에 가짜 고리를 만들어
오히려 부정확했다. **세리프 폰트(Noto Serif KR, 같은 notofonts/noto-cjk
OFL 패밀리) 하나를 템플릿 뱅크에 추가**하니 즉시 해결: T1 44.4%(불변)
vs T2 **50.0%**로, 격차가 사실상 사라졌다.

### 실패 3(진단) → OVERGEN 오염, 기존 인프라로 이미 해결돼 있었음

일부 저점수 오답("쟤"→"걣" 0.46, "촜"→"뺾" 0.51)을 육안 확인한 결과
**단일 글자가 아니라 Seedream이 2~3글자를 과생성한 이미지**였다(예:
"쟤" 요청에 "재배" 두 글자 렌더링). template_match가 다중 글자 뭉치를
억지로 단일 템플릿에 끼워 맞추려다 생긴 오염이지, 판정 로직의 결함이
아니다. 확인해보니 **CLOVA의 기존 OVERGEN 판정(`score.py`의
`len(pred)>1`)이 이미 이 케이스를 정확히 잡고 있었다** — Route B 268건
중 OVERGEN 12건(4.5%). 새 로직을 만들 필요 없이 기존 OVERGEN 판정으로
제외하면 됐다(간단한 종횡비 휴리스틱은 시도했으나 "정상 음절의 초성+중성
/종성 분리"와 "실제 다중 글자"를 구분 못 해 폐기).

### 최종 검증 — 같은 256장(OVERGEN 제외)으로 3자 공정 비교

| 판정자 | 정확도 |
|---|---|
| CLOVA (occ 0.28, 8단계 이전 설정) | 32.4% |
| CLOVA (occ 0.10, 오늘 확정한 적정값) | 42.6% |
| **템플릿 매칭 (soft-IoU + 3폰트)** | **52.0%** |

템플릿 매칭이 제대로 보정된 CLOVA보다도 9.4%p 높다. CLOVA는 여전히
T1/T2 격차가 남지만(47.1% vs 38.7%) 템플릿 매칭은 세리프 추가 후
격차가 거의 없다(52.1% vs 51.8%). 비용은 0원(로컬), 사전 편향은
구조적으로 불가능.

### 아직 안 끝난 것

- **template_match 자체의 사람 감사 검증 미실시** — CLOVA·VLM에는 180문항
  골드셋을 돌렸지만 template_match는 아직 "target과 일치하는가"만 확인,
  "사람이 봐도 맞다고 하는가"는 미검증. 남은 오답(48%)이 진짜 모델
  실패인지 template_match 자체 오류인지 완전히 분리되지 않았다(퐋·갔
  등 일부만 육안 확인).
- template_match 내부에 자체 다중 글자 감지가 없다 — 현재는 CLOVA의
  OVERGEN 판정에 의존(완전히 독립적인 판정자는 아직 아님).
- 아직 Judge Ceiling(judge_ceiling.py)으로 셀별 공식 검증은 안 함 —
  특히 CLOVA가 0%였던 희귀 겹받침 셀에서 template_match가 실제로
  얼마나 나오는지가 핵심 질문으로 남아 있음.

결과 파일: `results/template_match_full_eval.json`,
`results/clova_occ010_full_eval.json`.

## 10단계 — 실제 생성물 사람 감사 → 하이브리드 판정자 확정

### 실제 Seedream 이미지로 사람 감사 (9단계는 폰트 렌더링이라 순환 검증)

`audit_queue.build_pilot_audit_queue()` + `scripts/audit_server_pilot.py`
(포트 8878) 신규 구축 — 파일럿 256건(OVERGEN 등 제외) 전체를 실제
이미지로 target-blind 판독. CLOVA·template_match가 서로 다르게 읽은
160건을 우선 배치.

**1차 결과(사람이 "한글"로 판정한 것만 정답 허용, 256건 전수)**

| | 정확도(vs 타깃) | 사람과의 일치율 |
|---|---|---|
| **사람 (진실)** | **64.5%** | — |
| CLOVA | 42.6% | 46.5% |
| template_match | 52.0% | 58.2% |

종성 유형별 사람(진실) 정확도: 없음 75.9% / 단순종성 65.1% / 겹받침
49.3% — "초성 보존·종성 붕괴" 패턴이 **판정자 편향 없이, 사람 기준으로
처음** 재현됨.

### 반례 제기와 재분석 — "읽을 수 없음"의 정체

사용자가 사람 감사 중 "읽을 수 없음"으로 표기한 문항 상당수가 실은
**애초에 한글이 아닌 출력**이었다고 지적. 재분석 결과:

- 256건 중 **44건(17.2%)을 사람이 "한글 아님/읽기 불가"로 판정**
- 그런데도 CLOVA·template_match는 **둘 다 강제로 한글 하나를 답함**
  (개방형 인식이든 폐쇄형 검증이든, 후보 집합이 "11,172자 중 하나"라서
  "해당 없음"을 답할 수 없는 구조적 결함)
- 위양성(사람이 한글 아니라 했는데 판정자가 "정답"이라 답한 것): CLOVA
  2건(1.8%), template_match 5건(3.8%) — 정확도 수치를 크게 부풀리진
  않음
- template_match의 유사도 점수로 이 44건을 걸러보려 했으나 실패 —
  오답 점수 분포가 크게 겹침(한글로 읽힌 오답 중앙값 0.734 vs 한글
  아닌 것 중앙값 0.642, 분리 임계값 없음)

**결론**: 두 판정자 모두 "이건 한글이 아니다"를 답할 능력이 없다 —
아직 해결 못 한 진짜 한계로 남긴다.

### 하이브리드 판정자의 자격 재검증 — 절대 정확도가 아니라 오차의 방향

64.5%는 설계서 §14.2의 공식 점수 하한(85%)에 크게 못 미친다 — **하이브리드를
"이 모델의 정확도는 X%"라고 절대 주장하는 데 쓸 수는 없다.** 그러나
6단계에서 이미 확립한 판정자 자격 기준은 절대 정확도가 아니라
**"오차가 측정 축과 상관되지 않는가"**였다. 이 기준으로 다시 보면:

| 종성유형 | 사람 | CLOVA 오차 | template_match 오차 | 하이브리드 오차 |
|---|---|---|---|---|
| no_T | 75.9% | +6.0%p | +21.7%p | +6.0%p |
| simple_T | 65.1% | +24.5%p | +8.5%p | +8.5%p |
| cluster_T | 49.3% | +37.3%p | +7.5%p | +7.5%p |
| **오차 변동폭** | | **31.3%p** | 14.2%p | **2.5%p** |

하이브리드는 대체로 일정한(±2.5%p) 편향만 남고, 축을 따라 흔들리지
않는다. 그 결과 **RQ2/RQ3의 핵심 대비(겹받침 vs 단순종성 정확도 차)를
정확히 복원**한다:

```
겹받침 − 단순종성 정확도 차이
  사람(진실)   −15.8%p
  하이브리드   −14.8%p  (오차 +1.0%p)   ← 구조 비교엔 신뢰 가능
  CLOVA 단독   −28.6%p  (오차 −12.8%p)  ← 겹받침 효과를 1.8배 과장
```

**즉 하이브리드는 절대 눈금은 못 믿어도(6~8.5%p 낮게 나옴, 항상 같은
방향), 눈금 간격(구조 축 간 비교)은 믿을 수 있는 자(ruler)다.** 이는
JAMO의 Primary 지표(§8.6: OCR-derived Jamo Error Rate, Complex-final
Acc gap)가 원래 요구하는 것과 정확히 일치한다 — 절대 정확도 리더보드가
아니라 구조적 실패 패턴 비교가 핵심 기여였다.

### 구현: `jamo_bench/hybrid_judge.py`

- `route_judge(target)`: 타깃의 `coda_class_3`(무종성/단순종성/겹받침)로
  CLOVA vs template_match 중 무엇을 쓸지 결정 — 빈도 코퍼스 불필요,
  이미 계산되는 구조 메타데이터만 사용.
- `combine(target, clova_reading, template_match_reading)`: 순수 함수로
  라우팅 결과 조립. 실측 편향값(`MEASURED_BIAS_PP`)을 상수로 박아
  결과에 항상 동봉 — 사용자가 "이 셀은 몇 %p 낮게 나온 값"인지 매번
  알 수 있게 강제.
- `read_hybrid(image, target, clova_fn, template_match_fn)`: 라우팅에
  필요한 판정자만 실제로 호출(API 비용 절감 — 파일럿 기준 종성 있는
  타깃이 67%라 CLOVA 호출이 그만큼 줄어듦).
- 10개 테스트 추가(155개 전체 통과).

### 아직 남은 것

## 11단계 — CLOVA confidence 활용 검증

사용자 제안: CLOVA의 `inferConfidence`(이미 `OcrField.confidence`로
받아오고 있었으나 여태 버려지고 있었음)를 "이게 한글이 아니다"를
걸러내는 신호로 쓸 수 있는가? 10단계에서 남긴 유일한 미해결 문제였다.

같은 256장에 CLOVA를 다시 돌려 confidence를 캡처하고 사람 감사 라벨과
대조(`results/clova_confidence_eval.json`).

**"정답 여부" 신호로는 강하다** — 정답 평균 confidence 0.966, 오답
평균 0.677. 임계값 0.90 이상만 채택하면 정밀도 43.3%(기준선)→75.9%.

**"한글 여부" 신호로는 못 쓴다** — 오답만 따로 떼어 비교하면:

| | 평균 confidence |
|---|---|
| 오답 + 애초에 한글이 아님 | 0.696 |
| 오답 + 진짜 한글을 잘못 읽음 | 0.669 |

거의 동일하다. CLOVA는 완전히 엉뚱한 기호를 볼 때도 진짜 한글을
잘못 읽을 때만큼 자신만만하다 — 10단계에서 발견한 "한글 아닌 출력을
못 걸러낸다"는 한계는 confidence로도 해결되지 않는다.

**반영**: `match_region.MatchResult`에 `candidate_confidence` 필드를
신규 노출(이전엔 계산만 되고 버려짐). 신뢰 게이트로만 쓰도록 필드
docstring에 실측 수치와 함께 오용 방지 주석 명시. 157개 테스트로 확장.

## 12단계 — "한글 아님"의 정체 규명, 정형성(well-formedness) 신호 발견

### 라벨 의미의 재확인 — 10단계의 "17.2%가 한글 아님"은 부정확한 표현이었다

10·11단계가 "두 판정자 모두 '이건 한글이 아니다'를 못 답한다"를 유일한
미해결 문제로 남겼는데, 정작 **그 44건을 눈으로 본 적이 없었다.** 전수
확인 결과 거의 전부가 **또렷하게 잘 그려진 한글꼴 글자**였다.

감사자에게 `illegible` 선택 기준을 직접 확인한 결과: **"윈도우 키보드로
입력이 불가능한 형태"** — 즉 주관적 "읽을 수 없음"이 아니라 **11,172
완성형 집합의 원소가 아님**이라는 정확하고 재현 가능한 기준이었다.

결정적 사례 2건:

- target `감`: CLOVA·template_match **둘 다 `감`으로 정답 처리**. 그러나
  받침 ㅁ이 안에 십자획이 들어간 `田`으로 그려져 입력 불가능한 형태다.
- target `퉑`: 이미지는 명백히 `웖`(초성 ㅇ)인데 template_match가 `퉑`이라
  답해 데이터에 `tmOK=True`로 **정답 계상**돼 있었다.

**따라서 문제의 정의가 바뀐다.**

| | |
|---|---|
| ✗ 기존 정의 | 판정자가 "한글 아님"을 못 답한다 |
| ✓ 실제 정의 | 판정자가 **malformed glyph를 가장 가까운 유효 음절로 스냅한다** |

이는 판정자의 결함일 뿐 아니라 **모델의 가장 심각한 실패(존재하지 않는
글자를 그림)를 판정자가 은폐하는** 구조다.

한편 감사자가 일관된 명시적 기준을 적용하고 있었으므로 **64.5%와
하이브리드 편향 6~8.5%p는 그대로 유효**하다(라벨 의미가 흔들려 근거가
무너진 것이 아니다). 다만 라벨 **이름**(`illegible`)이 실제 기준을 전혀
표현하지 못하므로, 2번째 감사자에게 같은 UI를 주면 다른 기준으로 누르게
되어 Krippendorff α가 무의미해진다 — 라벨 체계 개편이 선행돼야 한다.

### 정형성 신호 3종 신설 (`template_match.py`)

`TemplateReading`에 필드 추가(하위 호환, 157개 테스트 통과):
`per_font`, `font_agreement`, `margin`, `unexplained_ink`, `missing_ink`.

핵심은 **`unexplained_ink`** — soft-IoU는 대칭이라 "여분의 획"이 합집합
분모에 희석되지만, 방향을 준 잔차(최적 템플릿의 2px 여유 밖에 있는 잉크
비율)는 `감`의 田 십자획 같은 것에서 곧바로 튄다. 감사자가 적용한 기준
("획이 더 있어 입력 불가능")과 지표가 일대일로 대응한다.

**모든 신호는 target-independent로 제한했다.** 타깃 순위·타깃과의
편집거리를 섞으면 "정답에 가까우면 통과"가 되어 자동 판정 구간이 정답
쪽으로 선별되고 정확도가 인위적으로 부풀려진다(11단계에서 CLOVA
confidence 게이트가 정밀도를 43.3%→75.9%로 올린 것도 판정 개선이 아니라
같은 selection effect였다).

### 실측 — 256장, 사람 라벨(유효 212 / 무효 44) 기준

| 신호 | AUC | 무효 중앙값 | 유효 중앙값 |
|---|---|---|---|
| **unexplained_ink** | **0.865** | 0.115 | 0.016 |
| score (대조군) | 0.847 | 0.649 | 0.765 |
| margin | 0.696 | 0.011 | 0.025 |
| **font_agreement** | **0.440** | 0.667 | 0.667 |

**가설 하나가 기각됐다.** "진짜 유효 음절이면 3개 폰트 뱅크가 독립적으로
같은 음절을 뽑을 것"이라는 `font_agreement`는 **AUC 0.440으로 무작위보다
못했다.** 반대로 10단계가 "분리 임계값 없음"으로 폐기했던 raw score는
실은 AUC 0.847로 쓸 만했다 — 당시엔 *깨끗한* 분리를 기대하고 중앙값만
비교해 포기했던 것이다.

운용점(`unexplained_ink >= 0.102 OR score <= 0.661`):

| | 무효 검출률 | 유효 오탐률 | 사람 큐 |
|---|---|---|---|
| 채택 운용점 | 72.7% | 14.6% | 24.6% |

### 한계 — 게이트 실패가 측정 축과 상관된다

| 종성유형 | n | 무효율(사람) | 게이트 발화율 | **검출률** |
|---|---|---|---|---|
| no_T | 83 | 10.8% | 25.3% | 88.9% |
| simple_T | 106 | 18.9% | 23.6% | 75.0% |
| cluster_T | 67 | 22.4% | 25.4% | **60.0%** |

**사람 큐 부담은 축 전반에 균일(23.6~25.4%)해서 좋다.** 그러나 **검출률이
겹받침에서 가장 낮다** — 무효 출력이 가장 많은 곳에서 가장 못 잡는다.
잔여 오염은 cluster_T 9.0% vs no_T 1.2%로 **축을 따라 약 7.8%p 차이**가
남는다. 6단계에서 세운 판정자 자격 기준("오차가 측정 축과 상관되지 않을
것")을 아직 완전히는 만족하지 못한다.

또한 **template_match 위양성 5건 중 4건을 게이트가 놓쳤다**(`퉑`·`죇`×2·
`쀆`). 판정자가 "정답"이라 답한 무효 글자가 가장 위험한 케이스인데
바로 그것이 잘 안 잡힌다.

**판정: 자동 무효 처리(silent auto-reject)에는 쓸 수 없고, 사람 감사
큐 라우팅에만 쓴다.** 능력이 0이던 상태에서 검출률 72.7%로 올라간 것은
실질적 진전이지만, 1번 과제는 부분 해결이다.

결과 파일: `results/wellformedness_eval.json`,
스크립트: `scripts/eval_wellformedness.py`.

## 13단계 — 파일럿 300장 라벨 완결, 실패 유형의 정체 확정

`scripts/audit_server_pilot2.py`(포트 8879) + `audit_ui_pilot2.html` 신규.
라벨 5종(`audit_queue.PHASE2_LABELS`)으로 87문항 감사 — **미감사 44장**
(Route A1/C·OVERGEN, 사람이 한 번도 본 적 없던 집단) + **재라벨링 43장**
(1차에서 `illegible`로 뭉쳐 있던 것).

### "한글 아님 17.2%"의 정체 — 86%가 malformed였다

1차 `illegible` 43건의 실제 분해:

| | 건수 | 비율 |
|---|---|---|
| **malformed**(한글 구조, 획이 틀림) | **37** | **86.0%** |
| non_hangul | 3 | 7.0% |
| multi_syllable | 3 | 7.0% |

10단계가 "한글이 아닌 출력"이라 부른 것은 **거의 전부 한글 구조를 갖춘
malformed glyph**였다. 12단계의 진단이 정량적으로 확인됐다.

감사자 메모가 실패 유형을 그대로 보여준다 — `'탑'으로 보이지만 'ㅂ' 종성
획이 하나 생략됨`, `'츼'로 보이지만 'ㅡ'에 알수없는 획들이 추가돼있음`,
`'푼'과 '폰'의 합성임`, `한 글자의 구성이 '포ㅒㄳ'으로 돼있음`.

### 파일럿 300장 최종 라벨 (v1/v2/1차 감사를 통합)

| 라벨 | 건수 | 비율 |
|---|---|---|
| valid_syllable | 235 | **78.3%** |
| malformed | 42 | 14.0% |
| non_hangul | 13 | 4.3% |
| multi_syllable | 10 | 3.3% |

**Seedream 출력의 21.7%가 유효 완성형이 아니며, 그 대부분(14.0%p)이
malformed다.** 모델의 지배적 실패는 "틀린 글자"가 아니라 "존재하지 않는
글자"이고, 판정자는 그것을 가장 가까운 유효 음절로 스냅해 은폐한다.

### Route는 non_hangul엔 유효, malformed엔 무력 — 역할 분담이 드러났다

미감사 집단(Route A1/C·OVERGEN)과 재라벨링 집단의 구성이 다르다:

| 집단 | non_hangul 비율 |
|---|---|
| 미감사 (Route A1/C·OVERGEN) | 10/44 = **22.7%** |
| 재라벨링 (Route B) | 3/43 = **7.0%** |

Route C/A1은 non_hangul을 3배 이상 농축한다. 그러나 단독 필터로는 약하다:

```
A1+C 자동 배제 시 — 정밀도 46.9% / 재현율 23.1% / 유효 7.2%를 잘못 버림
```

정형성 게이트(12단계)를 세분화된 라벨로 재평가하면 **정확히 상보적**이다:

| 라벨 | n | 게이트 검출률 | unexplained_ink 중앙값 |
|---|---|---|---|
| valid_syllable | 212 | 14.6% *(오탐률)* | 0.016 |
| malformed | 37 | **70.3%** | 0.114 |
| non_hangul | 3 | 100.0% | 0.161 |
| multi_syllable | 4 | 75.0% | 0.092 |

**역할 분담 확정:** Route → non_hangul / 정형성 게이트 → malformed /
2-split → multi_syllable. 세 실패 유형이 각각 다른 탐지기를 요구한다.

### 남은 하드코어 — 획 하나 차이

판정자 위양성 5건(무효인데 타깃과 일치)의 세부를 보면 4건이 malformed이고
`unexplained_ink`가 0.019~0.083으로 낮다(`퉑`·`죇`·`쀆`). 감사자 메모의
"종성 획이 하나 생략됨" 유형이며, 획 하나 차이는 현재 신호의 검출 하한
근처다. **가장 위험한 케이스(판정자가 자신 있게 정답이라 답하는 무효
글자)가 가장 안 잡힌다**는 12단계의 관찰이 유지된다.

### 라벨 체계 문제 — malformed / non_hangul 경계가 신뢰 불가

감사자가 **"non_hangul 기준이 아리송하다, 한글 구조를 유지하는 듯 아닌 듯한
것이 많다"**고 보고했고, 메모가 이를 뒷받침한다(non_hangul 사례 설명이
`한글 구조에 알 수 없는 도형이 섞여 있음`). malformed→non_hangul은 이분법이
아니라 연속체다.

**대응: 1차 라벨을 이진으로 확정한다.**

```
Primary  : valid_syllable / invalid / multi_syllable / no_text
           ("윈도우 키보드로 입력 가능한 완성형 한 글자인가" — 1·2차에서
            일관되게 적용된 유일한 기준)
Secondary: invalid 내부의 malformed vs non_hangul (exploratory, 신뢰도 낮음 명시)
```

2번째 감사자의 Krippendorff α는 **이진 기준으로 산출**하고, 3분류 α는
참고값으로만 병기한다. 이 구분 없이 5분류로 α를 내면 신뢰할 수 있는 축까지
경계 불일치에 끌려 낮게 나온다.

결과 파일: `results/audit/human_audit_pilot_phase2.jsonl`.

## 14단계 — 2번째 감사자, Krippendorff's α 산출, "multi_syllable" 범주 붕괴

Phase 2 큐(87문항)를 2번째 감사자가 독립적으로 완료. 서버(`audit_server_pilot2.py`,
포트 8879)의 감사자 식별이 `localStorage` 기반이라 같은 브라우저에서
새로고침하면 이전 감사자로 계속 인식되는 문제가 있었다 — `?annotator=` 쿼리
파라미터로 우회(코드 수정 없이 해결, UI 버그로 별도 기록만 남김).

### 이진 기준은 매우 신뢰 가능, 세부 분류는 신뢰 불가

87문항 공통 응답에 대해 Krippendorff's α(명목형, 2감사자, 결측 없음) 계산:

| 분류 수준 | α | Landis–Koch/Krippendorff 판정 |
|---|---|---|
| **이진 (valid_syllable / 그 외)** | **0.942** | 매우 신뢰 가능 |
| 4분류 (valid/invalid/multi_syllable/no_text) | 0.576 | **신뢰 불가**(α<0.667) |
| 5분류 (원본 라벨 그대로) | 0.515 | 신뢰 불가 |

이진 raw 일치율 97.7%(85/87). 13단계에서 "1차 라벨을 이진으로 확정한다"고
내린 결정이 실측으로 정당화됐다.

### 불일치의 정체 — malformed ↔ multi_syllable 경계 하나에 집중

세부 혼동표에서 불일치 21건 중 17건(81%)이 한 지점에 몰렸다:

| 1차 | 2차 | 건수 |
|---|---|---|
| **malformed** | **multi_syllable** | **17** |
| malformed | non_hangul | 6 |
| non_hangul | no_text | 2 |
| (기타) | | 4 |

**87건 중 17건(19.5%)에서 "획이 틀린 글자 하나"와 "두 글자가 붙음"이
갈렸다.** 여분의 획이 많으면 두 서술이 같은 그림을 다르게 표현하는 것일
수 있어, 사람에게도 원리적으로 모호한 경계다.

### 결론 — `multi_syllable`을 주관적 라벨로 두면 안 된다

13단계가 제안한 4분류(valid/invalid/multi_syllable/no_text)를 1차 기준으로
쓰려던 계획을 기각한다. `multi_syllable`이 malformed와 20%가량 혼동되는
이상, **OVERGEN(2번 과제) 탐지기의 "정답"을 "사람이 몇 글자라고 느꼈는가"로
정의할 수 없다** — 사람 자신이 그 축에서 불안정하기 때문이다. 대신 "잉크가
공간적으로 몇 덩어리로 분리되는가"라는 기계적 정의로 바꿔야 한다(아래
15단계).

**확정된 유일한 1차 기준:** 이진(유효 완성형 한 글자인가). 세부 4·5분류는
전부 exploratory로 강등하고 신뢰도 낮음을 명시한다.

결과 파일: `results/audit/human_audit_pilot_phase2.jsonl`
(`annotator` 필드로 두 감사자 구분).

## 15단계 — OVERGEN 2-split 실패, 판정 프로토콜 확정, 범위 축소

### OVERGEN 자체 감지 — 음성 결과로 폐기

14단계에서 사람의 `multi_syllable` 라벨을 정답으로 못 쓴다고 판정했으므로,
`jamo_bench/overgen.py`를 **기계적 정의**로 구현했다 — "잉크가 공간적으로 몇
덩어리로 분리되는가, 그 덩어리를 각각 독립 음절로 읽는 게 전체를 한 음절로
읽는 것보다 유효 음절 템플릿에 더 잘 맞는가"(연결요소 분석 + 2-split
template match). 정답은 다중 출처 약한 신호로 구성(strict = 두 감사자 일치
또는 CLOVA와 한 감사자 일치, n=8 / loose n=39 / valid 대조군 230).

`merge_iterations` 4종 × `margin` 5종 = 20개 조합 전수 스윕 결과:

| merge_it | margin | strict recall | loose recall | valid 오탐 |
|---|---|---|---|---|
| 30 | 0.00 | **12.5%** | 10.3% | 0.4% |
| 6 | 0.00 | 12.5% | **15.4%** | 2.2% |

**모든 조합에서 검출률 최대 15%.** 원인은 구조적이다 — Seedream의 다중 글자
출력은 공간적으로 떨어져 있지 않고 **서로 붙거나 겹쳐서** 그려진다(`쫄읙`,
`갈읙`). 연결요소로 분리가 불가능하다. 2026-08-10 검토안이 제안하고 채택했던
아이디어이며, "정상 음절의 초성+중성/종성 분리와 실제 다중 글자를 구분한다"는
전제 자체가 이 데이터에서 성립하지 않았다.

**폐기한다.** 코드(`overgen.py`)와 스크립트(`eval_overgen.py`)는 음성 결과의
재현을 위해 남기되 파이프라인에는 넣지 않는다. OVERGEN은 파일럿 기준 3.3%로
실패 유형 중 가장 작고, 정답 신뢰도도 가장 낮다(α 0.576).

### 판정 프로토콜 확정 — CLOVA confidence 게이트 + 사람

사용자 제안: "CLOVA로 판정하되 confidence가 낮은 것만 사람이 본다."
기존 데이터(`clova_confidence_eval.json` + 사람 라벨)로 즉시 검증 가능했다.

**11·12단계의 경고가 실측으로 기각됐다.** 12단계에서 "정답 여부와 상관된
신호로 abstain하면 자동 판정 구간이 정답 쪽으로 선별되어 정확도가 부풀려진다"
고 했는데, 실제로는 반대로 작동한다:

| 종성유형 | 자동 채택률 | 그 구간 사람↔CLOVA 일치율 |
|---|---|---|
| no_T | 75.9% | 93.3% |
| simple_T | 55.2% | 84.9% |
| cluster_T | **18.8%** | 81.8% |

**CLOVA는 자기가 못 믿을 곳에서 정확히 자신감을 잃는다.** 어려운 구간이
통째로 사람에게 넘어가므로 편향이 커지는 게 아니라 줄어든다. 은폐(무효
글자를 정답으로 처리)는 자동 채택 133장 중 0건(95% 상한 약 2.2%).

`scripts/eval_confidence_gate.py`로 임계값 스윕(n=256):

| 임계값 | 사람 큐 | 전체 편향 | 편향 변동폭 | 격차 복원 오차 |
|---|---|---|---|---|
| 0.70 | 35.5% | −5.1% | 5.3% | −5.2%p |
| **0.80** | **42.2%** | **−3.5%** | **1.6%** | **−1.6%p** |
| 0.90 | 48.0% | −2.7% | 2.1% | +1.3%p |
| 0.99 | 70.3% | −0.8% | 1.2% | +0.9%p |
| 사람 전수 | 100% | 0 | 0 | 0 |

선택 기준을 "편향 변동폭 최소"로 두면 전수 사람 판정(변동폭 0)으로 수렴해
자동화의 목적이 사라진다. **품질을 제약으로 걸고 비용을 최소화**하도록
바꿨다 — 격차 복원 ±5%p & 변동폭 ≤2.5%p를 만족하는 것 중 사람 큐 최소.
**확정: `CONFIDENCE_THRESHOLD = 0.80`.**

기존 hybrid_judge(편향 변동폭 2.5%p, 격차 오차 +1.0%p)보다 **변동폭이
1.6%p로 더 평평**하고, 종성유형별 판정자 라우팅이라는 복잡한 장치가
필요 없다. `jamo_bench/judging_protocol.py` 신설(9개 테스트, 166개 전체 통과).

**남은 한계:** 정형성(유효 완성형인가)은 여전히 사람만 판정한다. 자동 채택
구간에도 무효가 6.8% 섞여 있고 CLOVA는 이를 가장 가까운 유효 음절로 스냅한다.

### 범위 축소 — 증거 등급으로 재정렬

`docs/SCOPE.md` 신설. 요지:

- **좁힌 목표**: 절대 정확도 리더보드가 아니라 **"판정자가 모델의 가장 흔한
  실패(존재하지 않는 글자, 실측 21.7%)를 유효 음절로 스냅해 은폐한다"는 것을
  정량화하고, 사람 이진 검증(α=0.942) 기반 Gold 프로토콜을 제안**한다.
- **뺀 것**: Cross 다모델(RQ6), Forge 전체, Word 서브셋, private-test·리더보드
  ·OSF, OVERGEN, malformed/non_hangul 세부 구분, template_match/hybrid_judge.
- **대가**: 단일 모델 방법론 논문이 된다. 그 대신 §14.2 No-Go(공식 점수 하한
  85%)가 약점이 아니라 결과가 된다.

## 16단계 — 나머지 두 셀 축 검증, 쌍자음 초성에서 자기교정 실패 발견

15단계에서 confidence 게이트를 확정할 때 **편향을 종성 축으로만 쟀다.** 18셀은
2모음 × 3종성 × 3초성군인데 나머지 두 축은 확인한 적이 없었다. 프로젝트 큰그림을
재정리하면서 이 공백이 드러나 전수 검증했다.

### 초성군 축이 무너져 있었다

| 셀 축 | 편향 변동폭 | 판정 |
|---|---|---|
| 종성(coda) | 1.6%p | OK |
| 모음(vowel) | 3.1%p | 기준(2.5%p) 초과 |
| **초성군(onset)** | **10.4%p** | **명백한 실패** |

`tense_O`(ㄲㄸㅃㅆㅉ)에서 −11.1%p로, `simple_O`(−0.7%p)의 16배였다.
자동 채택 구간의 CLOVA↔사람 불일치율을 보면 원인이 분명하다:

| 초성군 | 자동 채택 구간 불일치율 |
|---|---|
| simple_O | 4.5% |
| aspir_O | 21.7% |
| **tense_O** | **47.4%** |

**쌍자음 초성 음절에서 CLOVA는 "자신 있게 틀린다."** 15단계에서 발견한
자기교정(못 믿을 곳에서 자신감을 잃음)이 이 구간에서만 작동하지 않는다.
오독의 정체를 보면 초성 자체는 보존하고(ㅉ→ㅉ, ㄸ→ㄸ) 중성·종성을 틀린다 —
쌍자음 음절의 실사용 빈도가 낮아 8단계의 희귀도 편향이 재현되는 것으로 보인다.

### 수정: `tense_O`를 자동 채택에서 제외

`NO_AUTO_ONSET_GROUPS = {"tense_O"}` 추가. `route()`에 `onset_group` 인자 신설.

| | 적용 전 | 적용 후 |
|---|---|---|
| 종성 축 변동폭 | 1.6%p | 1.5%p |
| 모음 축 변동폭 | 3.1%p | **0.5%p** |
| 초성군 축 변동폭 | 10.4%p | **1.9%p** |
| 전체 편향 | −3.5%p | **−0.8%p** |
| 사람 큐 | 42.2% | 50.0% |

사람 큐가 7.8%p 늘지만 **세 축이 전부 기준을 통과하고 전체 편향도 4배
줄었다.** `MEASURED_BIAS_PP`를 갱신(no_T 0.0 / simple_T −0.9 / cluster_T −1.5).

**한계 — in-sample 적합이다.** n=63(tense_O)에서 도출해 같은 데이터로
평가했다. 기전이 8단계와 일관되어 채택했지만 표본 보강 시 재검증한다.

### 자모 위치별 오류율(H4)은 조건부로만 쓸 수 있다

"초성/중성/종성 각각 성공률"을 프로토콜로 낼 수 있는지 처음 검증했다:

| | 사람(진실) | 프로토콜 | 왜곡 |
|---|---|---|---|
| Unconditional 초성−종성 격차 | +13.3%p | +17.2%p | **+3.9%p** |
| Conditional 초성−종성 격차 | +16.0%p | +19.3%p | **+3.3%p** |

**순서(초성 > 중성 > 종성)는 보존하지만 기울기를 과장한다.** 설계서 §6.6의
검출 하한(8%p)보다는 작아 H4의 **방향 검정에는 쓸 수 있으나, 절대 자모
오류율은 Gold split에서만** 인용해야 한다.

또한 자모 분해는 **유효 완성형에만 정의된다** — 무효 글자(21.7%)는 판정자가
스냅한 결과라 그 분해가 허구다. Conditional(유효만, n=212)과
Unconditional(무효는 3위치 전부 오류, n=256)을 §8.5.1대로 반드시 병기한다.

### 부수 확인 — 전사 일치율 100%

2감사자가 **둘 다 유효 완성형이라고 판정한** 23건에서 전사 문자열이 100%
일치했다(23/23). 즉 판정 신뢰도가 두 단계로 깔끔하게 갈린다:

```
"유효 완성형인가"     → α = 0.942  (매우 신뢰)
"그래서 무슨 글자인가" → 100% 일치 (n=23, 유효 판정 건 한정)
"malformed냐 non_hangul이냐" → α = 0.52~0.58 (신뢰 불가)
```

## 17단계 — OSS OCR(EasyOCR) 교차검증, 은폐 현상이 CLOVA 특유가 아님을 확인

### 착수 이유

16단계까지의 증거는 CLOVA(한국 상용 OCR) 1종 + 자체 template_match뿐이었다.
"OCR 채점이 렌더링 실패를 은폐한다"를 방법론 비판으로 내려면, 실제 렌더링
논문(Qwen-Image, AnyText 등)이 쓰는 PaddleOCR/EasyOCR 계열에서도 같은 현상이
재현되는지가 관건이었다(`docs/SCOPE.md` "공개 프레이밍 재정의" 참고).

### 도구 선정 — 예상 못한 걸림돌 두 개

1. **RapidOCR(onnxruntime)를 먼저 설치했으나 기본 모델이 중국어 전용**이었다
   (`ch_PP-OCRv4`) — 한글 이미지에 `警`, `歌` 같은 한자를 답했다. 한국어
   인식을 명시적으로 지원하는 **EasyOCR**(`Reader(['ko','en'])`)로 전환.
2. **EasyOCR도 초기엔 전부 에러**(`'NoneType' object has no attribute
   'shape'`). 원인은 OpenCV가 Windows에서 **한글이 포함된 파일 경로를
   못 읽는** 고질적 버그(`cv2.imread`가 로컬 코드페이지로 fopen) — 이
   프로젝트의 이미지 파일명이 전부 `타깃음절_템플릿_...jpeg` 형식이라 전량
   실패했다. PIL로 읽어 numpy 배열로 넘겨 우회(`scripts/eval_oss_ocr.py`).

### 결과 — 파일럿 300장 전체(API 비용 0, Seedream 재생성 0)

| 지표 | 사람(진실) | CLOVA | EasyOCR |
|---|---|---|---|
| 유효 판정 정확도 (n=235) | — | 34.9% | 26.4% |
| **은폐율**(무효인데 유효 완성형으로 답함, n=65) | — | **76.9%** | **83.1%** |
| 은폐 + confidence≥0.80 | — | 38.6%(n=44*) | 18.5%(n=65) |
| 초성 오류율(Uncond.) | 30.7% | 19.7%(−11.0%p) | 40.3%(+9.7%p) |
| 중성 오류율(Uncond.) | 36.7% | 46.7%(+10.0%p) | 62.3%(+25.7%p) |
| 종성 오류율(Uncond.) | 42.0% | 58.0%(+16.0%p) | 63.7%(+21.7%p) |

*CLOVA confidence는 256장 부분집합만 측정돼 있어(15단계 유산) 미감사
44장분은 제외. EasyOCR은 300장 전체.

**은폐율이 아키텍처가 전혀 다른 두 판정자에서 거의 같다(76.9% vs 83.1%).**
CLOVA는 상용 폐쇄형 API, EasyOCR은 CRNN 기반 오픈소스로 학습 데이터·구조가
공유되지 않는다. 그런데도 "존재하지 않는 글자를 만나면 80% 안팎의 확률로
가장 가까운 유효 음절로 답한다"는 행동이 동일하게 나타난다.

**더 강한 증거 — 서로 다른 글자로 스냅한다.** 둘 다 답을 낸 44건 중
**77.3%(34건)는 서로 다른 글자**를 골랐다(예: `퐋`→CLOVA `쨰` / EasyOCR
`팩`). 같은 사전을 공유해서 같은 답으로 수렴하는 게 아니라, **"유효
음절 집합 중 하나를 반드시 골라야 한다"는 폐쇄형 인식 구조 자체가 원인**
이라는 뜻이다 — 특정 모델의 버릇이 아니라 인식 기반 판정자 일반의 문제.

**부가 확인 — 자모 위치별 오류율 방향이 판정자마다 다르다.** CLOVA는
초성을 사람보다도 더 잘 맞히는데(−11.0%p, 사전 지식으로 "그럴듯한 초성"을
보정) EasyOCR은 초성부터 사람보다 나쁘다(+9.7%p). 종성은 둘 다 크게
과소평가한다(+16.0 / +21.7%p). 이는 16단계에서 "자모 오류율은 조건부로만
쓴다"고 제한한 이유를 다른 판정자로도 재확인한 것이다 — **판정자에 따라
왜곡 방향 자체가 바뀌므로 자동 판정만으로는 절대 자모 오류율을 절대 인용
할 수 없다.**

### 결론 — 프레이밍 재정의의 핵심 전제가 성립

"인식 기반 판정자(OCR·형태매칭 불문)는 렌더링 실패를 조용히 은폐한다"는
주장을 CLOVA 국한이 아니라 **인식 기반 판정자 일반**으로 일반화할 수 있는
최소 증거를 확보했다. 다만 n=2(CLOVA, EasyOCR)이므로 "일반"이라는 표현은
"두 개의 독립적 아키텍처에서 재현됨"으로 신중하게 쓴다 — PaddleOCR 등
3번째 엔진 추가는 증거를 더 강화하지만 필수는 아니다.

결과 파일: `results/oss_ocr_eval.json`.
스크립트: `scripts/eval_oss_ocr.py`.

## 19단계 — 자기 주장 두 개를 실측으로 기각, 기여의 재정의

사용자 지적: *"복잡한 겹받침일수록 생성이 어렵다는 건 실험 안 해도 상식인데,
이걸 통계로 입증한 게 무슨 의의냐."* 정당한 지적이라 OCR 단독 채점과 정면
대조해봤고, **그 과정에서 이 프로젝트가 그동안 근거로 삼던 주장 두 개가
무너졌다.**

> ### 🔴 이 절의 "기각 1"·"기각 2"와 수치표는 18단계와 같은 버그의 산물이었다 (21단계에서 재정정)
>
> 18단계의 `pilot_results_v3.jsonl`을 진실값으로 썼는데 그 파일이 1차 미감사
> 44장을 전부 무효로 계상하고 있었다. 버그를 고치자 **기각 1이 다시 뒤집혀
> 원래 주장(10단계)이 옳았음이 확인**됐다. 아래 취소선 부분은 폐기하고
> 21단계의 재계산값을 쓴다.

### ~~기각 1 — "OCR로 재면 구조 격차가 왜곡된다"~~ → **철회. 원래 주장이 옳았다**

버그 있던 데이터에서는 진실 −21.1%p vs CLOVA −21.1%p로 "일치"해 보였다.
**버그 수정 후 재계산(21단계)하면 정반대다:**

```
겹받침 − 단순종성 격차 (unconditional, n=300)
  진실(사람)    −5.3%p
  CLOVA        −21.1%p   과장 −15.8%p  CI[−29.4%, −1.4%]  유의   배율 4.0x
  PaddleOCR    −17.5%p   과장 −12.2%p  CI[−25.3%, +1.7%]  n.s.   배율 3.3x
  EasyOCR      −11.9%p   과장  −6.7%p  CI[−21.1%, +7.8%]  n.s.   배율 2.3x
```

**세 엔진 모두 겹받침 페널티를 2~4배 과장한다.** 10단계의 원래 주장
("CLOVA가 겹받침 효과를 과장한다")이 옳았고, 19단계의 기각이 틀렸다.

### ~~기각 2 — "판정자가 무효를 정답 처리해 점수를 부풀린다"~~ → **부분 유지**

위양성 건수 자체는 여전히 적다(무효 65건 중 CLOVA 2, EasyOCR 3,
PaddleOCR 3). **"위양성이 점수를 크게 부풀리지는 않는다"는 유지**된다.

다만 21단계에서 **다른 경로의 부풀림**이 확인됐다 — 프로토콜의 Silver
구간(CLOVA 자동채택 128건)은 CLOVA가 답을 냈다는 이유로 전부 VALID로
계상되는데, 그중 16건(12.5%)이 사람 기준 무효다. 그래서 유효 완성형
생성률이 진실 78.3% → 프로토콜 83.7%로 **5.4%p 부풀려진다**. 위양성이
아니라 **"무효 판정 능력 부재"가 부풀림의 실제 경로**다.

### 그래서 실제로 남는 기여 세 가지 (21단계 재계산값)

```
                     진실    CLOVA   EasyOCR  PaddleOCR
no_T                70.0%    44.4%    43.3%     61.1%
simple_T            60.8%    30.0%    17.5%     27.5%
cluster_T           55.6%     8.9%     5.6%     10.0%
전체                62.0%    28.0%    21.7%     32.3%
겹받침−단순 격차     −5.3%   −21.1%   −11.9%    −17.5%
```

**(1) 절대 수준을 대폭 과소평가하고, 그 폭이 복잡도에 따라 커진다.**
과소평가 폭(진실 − OCR, 쌍대응 bootstrap):

| | no_T | simple_T | cluster_T |
|---|---|---|---|
| CLOVA | +25.6%p | +30.8%p | **+46.7%p** |
| EasyOCR | +26.7%p | +43.3%p | **+50.0%p** |
| PaddleOCR | +8.9%p | +33.3%p | **+45.6%p** |

전 구간에서 CI가 0을 배제한다. 겹받침에서 진실 55.6% vs CLOVA 8.9% —
"거의 못 그린다"와 "절반은 그린다"는 완전히 다른 결론이다.

**(2) 과소평가가 복잡도와 상관되므로 구조 격차까지 과장된다.** 위 기각 1
참고 — 2~4배. 게다가 **엔진마다 과장 배율이 다르다**(2.3x~4.0x)는 것은
서로 다른 OCR을 쓴 논문끼리 수치 비교가 성립하지 않는다는 뜻이다.

**(3) 실패의 종류를 구분하지 못한다.**

| 종성유형 | 정답 | 유효하지만 오답 | **없는 글자** |
|---|---|---|---|
| no_T | 70.0% | 13.3% | 16.7% |
| simple_T | 60.8% | 15.0% | 24.2% |
| cluster_T | 55.6% | 21.1% | 23.3% |

전체의 21.7%가 "존재하지 않는 글자"인데, OCR 채점에서는 이 칸이 통째로
사라져 전부 "오답"으로 뭉개진다. **점수는 나오지만 진단은 안 된다.**
(단 무효 비율이 종성 복잡도에 따라 단조 증가하지는 않는다 — 18단계 정정 참고.)

### 기여의 정확한 표현

우리가 입증한 것은 **"감"이 아니라 "자(ruler)"다.**

> 체중계로 "뚱뚱한 사람이 더 무겁다"를 재는 건 무의미하다. 그런데 그
> 체중계가 무거운 사람일수록 부정확하다면 "얼마나 더 무거운가"를 못 잰다.
> 이 프로젝트가 한 일은 몸무게를 잰 게 아니라 체중계를 검증한 것이다.

검증 3종: 눈금 균일성(18셀 세 축 편향 변동폭 1.5/0.5/1.9%p) · 기준의
비자의성(2감사자 α=0.942) · 도구 비의존성(아키텍처가 다른 EasyOCR·
PaddleOCR에서 은폐율 83.1%·78.5% 재현).

**그리고 이 검증이 실제로 오귀속을 세 번 막았다:** 7단계에서 "CLOVA가
겹받침을 3.3%밖에 못 읽는다"를 모델 탓으로 결론지을 뻔했으나 8단계에서
원인이 **글자 크기**였음이 드러났고(크기 보정 후 실사용 겹받침 100%),
19단계에서는 우리 자신의 주장 두 개를 기각했으며, 21단계에서는 **그 기각
자체가 데이터 로딩 버그의 산물이었음**을 잡아냈다.

**따라서 헤드라인은 "겹받침이 어렵다"가 아니라 "그 어려움을 지금까지의
방식으로는 제대로 잴 수 없었다"이다.**

## 20단계 — 합성 malformed 실험 완료: H1의 첫 진짜 통계적 입증

### 설계 — 이 프로젝트에서 유일한 "진짜 실험"

`jamo_bench/synthetic_malformed.py` + `scripts/eval_synthetic_malformed.py`.
생성 모델을 아예 쓰지 않고, 깨끗한 폰트 렌더링(대조군)과 국소적으로만 조작한
렌더링(실험군)을 **같은 글자에 대해 쌍으로** 만든다 — 대응표본(paired) 설계.

```
대조군   : 손대지 않은 렌더링 (n=84, 42음절 × 2폰트)
실험군   : add_stroke(획 추가) / remove_stroke(획 삭제)
           × mild/moderate/severe (n=497, 사후검증 거부 7건 제외)
통제 변수: 폰트·해상도·글자 크기·잉크 총량 — 같은 글자를 그대로 사용
무작위화 : 음절·조작 위치·정도 전부 seed 기반 난수
정답 보장: 구성상 무효(획을 실제로 더하거나 뺐음) + template_match
           사후검증으로 "우연히 다른 진짜 글자를 재구성"한 표본만 제외
```

### 결과 — H1 검정: "판정자는 존재하지 않는 글자를 존재하는 글자만큼
자신 있게 유효로 답한다"

**EasyOCR(개방형 — '답 없음' 가능)**

| | 답변율(뭔가 유효 음절로 답함) | n |
|---|---|---|
| 대조군 | 96.4% | 84 |
| 실험군(malformed) | 93.0% | 497 |

차이 −3.5%p, 2-비율 z검정 **p=0.234 — 유의하지 않음.** 단순히 "기각 실패"로
끝내지 않고 **동등성 검정**(TOST 방식, margin ±10%p)으로 확인: 차이의 95%
CI [−9.2%, +2.2%]가 margin 안에 완전히 든다 → **"구분하지 못한다"를 적극
입증.**

**더 결정적인 수치 — confidence 자체가 구분 신호를 안 담고 있다:**

| | EasyOCR confidence 평균 |
|---|---|
| 대조군 | 0.458 |
| 실험군(malformed) | 0.464 |

Mann-Whitney U 검정 **p=0.841.** 진짜 글자를 볼 때와 존재하지 않는 글자를
볼 때 **confidence 분포가 통계적으로 완전히 같다.** 11단계가 "confidence는
'한글 여부' 신호로 못 쓴다"고 실측(오답 내 한글/비한글 confidence
0.696/0.669, 거의 동일)했던 것을, 생성 모델 없이 통제된 조건에서 **정식
가설 검정으로 재확인**한 것이다.

**template_match(폐쇄형 — 항상 답함)**

| | 원본으로 스냅한 비율 |
|---|---|
| 대조군(자기 자신 정확도) | 96.4% |
| 실험군(malformed → 원본으로) | 94.0% |

차이 +2.5%p, p=0.367 — 유의하지 않음. **획을 추가하거나 지운 글자를
멀쩡한 원본과 통계적으로 구분하지 못한다.**

### 판정자가 완전히 무감각한 건 아니다 — 정도의 문제

remove_stroke의 mild(98.8%)와 severe(81.0%) 사이는 **유의하게 다르다**
(p=0.0002). 심하게 훼손하면 판정자도 결국 알아챈다. 다만 "심각한" 손상
수준(획 3개, bbox의 24%)에서도 여전히 81%가 스냅된다는 게 실사용적으로는
더 중요한 숫자다 — 실제 Seedream near-miss 실패는 이 mild~moderate 구간에
훨씬 가깝다(감사자 메모: "획 하나 생략", "십자획 하나 추가").

### 종성 축 패턴이 순수 합성 조작만으로 재현된다

EasyOCR 은폐율을 종성유형별로 보면:

| | 은폐율 |
|---|---|
| no_T | 88.1% |
| cluster_T | **95.2%** |

차이 +7.1%p, **p=0.019 — 유의함.** 13~18단계에서 실제 Seedream 이미지로
관찰한 "복잡한 종성일수록 무효 글자가 유효로 은폐되는 비율이 높다"는
패턴이 **생성 모델이 전혀 개입하지 않은 순수 합성 조작에서도 재현된다.**
이는 그 패턴이 Seedream의 특정 실패 스타일 때문이 아니라, **잉크(획)가
많을수록 국소적 손상이 판정자 눈에 덜 띈다는 판정자 구조 자체의 성질**
이라는 더 정확한 기전을 제공한다.

### 이게 왜 이 프로젝트에서 유일한 "진짜 실험"인가

지금까지의 다른 모든 발견(파일럿 300장 관찰, OSS OCR 교차검증)은 통계
교과서의 실험군/대조군/무작위배정/통제변수 틀에 들어맞지 않는 관찰 연구다
(교란변수 통제 불가 — 8단계에서 "겹받침이 어렵다"로 오귀속할 뻔했던 게
정확히 이 함정). 이 실험만이 **인과를 주장할 자격이 있는 설계**다.

결과 파일: `results/synthetic_malformed_eval.json`.

### 3번째 엔진(PaddleOCR) 추가 — 파일럿 교차검증과 합성실험 양쪽에

PaddleOCR 한국어 모델(`korean_PP-OCRv5_mobile_rec`)을 확보해 CLOVA·EasyOCR과
나란한 세 번째 독립 엔진으로 추가했다. Windows CPU 환경에서 기본값
(`enable_mkldnn=True`)이 `ConvertPirAttribute2RuntimeAttribute not support`
오류로 크래시해 `enable_mkldnn=False`로 우회(실측 확인).

**파일럿 300장 교차검증(17단계와 동일 방법론) — 세 엔진 수렴:**

| 지표 | CLOVA | EasyOCR | PaddleOCR |
|---|---|---|---|
| 유효 판정 정확도 | 34.9% | 26.4% | 40.0% |
| **은폐율**(무효인데 유효 완성형으로 답함) | 76.9% | 83.1% | **78.5%** |
| 위양성(무효인데 타깃과 정확히 일치) | 3/65 | 3/65 | **3/65** |

세 아키텍처(상용 폐쇄형 API·CRNN·PP-OCR)가 은폐율 77~83%, 위양성 3/65로
**거의 완벽하게 수렴한다.** 17단계의 n=2 증거가 n=3이 됐다.

**합성 malformed 실험(H1) 3번째 엔진 — 방향은 일치, 검정력은 약함:**

원래 규모(588건)로 4시간 넘게 실행해도 끝나지 않아(가속을 끈
`enable_mkldnn=False`의 속도 대가) 축소 규모(18음절×1폰트×3심각도=126건,
대조군 n=18)로 재실행:

| | 대조군 | 실험군(malformed) |
|---|---|---|
| 답변율/은폐율 | 88.9%(n=18) | 84.3%(n=108) |
| confidence 평균 | 0.669 | 0.591 |

차이 유의하지 않음(z검정 p=0.611), confidence 분포도 유의하지 않음
(Mann-Whitney p=0.351) — **방향은 EasyOCR 결과(p=0.234/0.841)와 일치**한다.
다만 대조군이 n=18로 작아 차이의 95% CI가 [−22.5%, +13.2%]로 넓어서,
EasyOCR에서 썼던 엄격한 동등성 검정(TOST, margin ±10%p)은 **통과하지
못한다** — 이건 "차이가 있다"는 증거가 아니라 **표본이 작아 검정력이
부족하다**는 뜻이다. **플래그십 통계 증거(p<0.05 수준의 확정적 동등성
입증)는 EasyOCR 결과(n=84)로 유지하고, PaddleOCR은 방향성 재현 증거로만
병기한다.**

종성유형별 은폐율(n=36씩)은 no_T 91.7% / simple_T 97.2% / cluster_T
63.9%로 — 이번엔 겹받침이 오히려 낮게 나왔다. n=36/그룹로 표본이 작아
17단계의 종성축 패턴(겹받침일수록 은폐율 높음, p=0.019)과 방향이 다른데,
이 역시 축소 재실행의 표본 크기 한계로 해석한다(원 스케일 재실행이나
seed를 바꾼 반복 실행으로 확인이 필요한 미해결 항목).

결과 파일: `results/oss_ocr_eval_paddleocr.json`,
`results/synthetic_malformed_paddleocr_eval.json`.

## 21단계 — 데이터 로딩 버그 발견, 18·19단계 결론 정정, 검증 스크립트 도입

### 발견 경위

기술노트 작성을 위해 **인용할 모든 수치를 원본에서 재확인**하던 중,
CLOVA 위양성이 기록(3건)과 다르게 2건으로 나오고, 사람 기준 무효(65건)와
v3 무효(72건)가 어긋나는 것을 발견했다.

### 버그 두 개

`rescore_pilot_v3.py`와 `eval_oss_ocr.py`의 `load_human_labels()`:

1. **Phase 2 전사를 버렸다.** `transcription = None  # phase2는 이진만 받고
   전사는 안 받음`이라 주석까지 달려 있었지만 **사실이 아니었다** — Phase 2
   UI는 `PHASE2_LABELS`의 `needs_transcription=True`에 따라 valid_syllable
   판정 시 전사를 받았고, 실제로 23건 전부에 전사가 저장돼 있었다.
2. **1차 미감사 44장이 통째로 누락됐다.** `for path, rec in phase1.items()`로
   순회해서, 13단계에 Phase 2로 처음 감사한 44장(Route A1/C·OVERGEN)이
   반환 dict에 아예 없었다. 호출부는 기본값 `{"valid": False}`로 처리해
   **전부 무효로 계상**했다. 그중 23장은 사람이 유효 완성형으로 판정한
   것이었다.

수정: `set(phase1) | set(relabel)` 합집합 순회 + 전사 보존.

### 결과 — 18·19단계 결론이 뒤집혔다

| 항목 | 버그 있던 값 | 정정값 |
|---|---|---|
| 유효 완성형 생성률(프로토콜) | 76.0% | **83.7%** |
| 유효 완성형 생성률(순수 사람) | — | **78.3%** |
| cluster_T 유효 완성형(사람) | 62.2% | **76.7%** |
| "겹받침이 유효 완성형을 못 그린다" | 24.5%p 낮음 | **−6.7%p, CI가 0 포함 → 기각** |
| 과소평가 폭 | "일정한 26%p" | **복잡도 따라 증가(+25.6 → +46.7%p)** |
| 구조 격차 왜곡 | "없음(−21.1 = −21.1)" | **2~4배 과장** |

**19단계에서 "기각"했던 10단계 주장("CLOVA가 겹받침 효과를 과장한다")이
사실은 옳았다.** 기각의 근거였던 데이터가 오염돼 있었다.

### 재발 방지 — `scripts/verify_claims.py`

기술노트·데이터셋 카드에 인용되는 **모든 수치를 원본에서 재계산**하는
단일 스크립트를 만들었다(C1~C10). 문서에 손으로 옮겨 적은 숫자와
불일치하면 문서가 틀린 것이다. 공개 릴리스의 재현성 장치이기도 하다.

### 교훈

이 프로젝트에서 **결과를 뒤집은 버그가 이번이 네 번째**다(5단계 Route
분류, 8단계 occupancy, 12단계 라벨 의미 오해, 21단계 데이터 로딩).
공통점은 전부 **"측정 파이프라인의 조용한 결함"**이었고, 모델 성능에 대한
잘못된 결론으로 직결됐다. 이는 이 프로젝트의 핵심 주장 — *"판정 파이프라인
을 검증하지 않으면 무엇을 재고 있는지 알 수 없다"* — 을 프로젝트 자신이
반복적으로 증명한 것이다.
